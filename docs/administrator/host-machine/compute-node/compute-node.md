# 컴퓨트 노드

**컴퓨트 노드** 메뉴에서는 Cloud:iA에 등록된 컴퓨트 노드의 상태와 리소스 정보를 확인하고, CPU 오버커밋 비율과 메모리 오버커밋 설정을 관리할 수 있습니다.
컴퓨트 노드 상세 화면에서는 리소스, 모니터링, 시스템 정보, 인스턴스, 스토리지 도메인 정보를 탭으로 구분하여 제공합니다.

---

## 컴퓨트 노드 목록

컴퓨트 노드 목록 화면에서는 등록된 컴퓨트 노드의 상태와 기본 운영 정보를 확인할 수 있습니다.

### 주요 작업

- **`편집`**: 노드를 한 개 선택했을 때 활성화됩니다. 클릭 시 **컴퓨트 노드 편집** 화면으로 이동합니다.
- **이름 클릭**: 선택한 컴퓨트 노드의 **상세 화면**으로 이동합니다.

> 💡 **참고:** 컴퓨트 노드 메뉴에서는 생성/삭제 기능을 제공하지 않으며, 편집 기능만 제공합니다.

### 테이블 컬럼

| 컬럼 | 설명 |
| --- | --- |
| **이름**          | 컴퓨트 노드 이름입니다. 클릭 시 상세 화면으로 이동합니다. |
| **상태**          | 현재 컴퓨트 노드 상태입니다. |
| **인스턴스 수**      | 해당 노드에 배치된 인스턴스의 수입니다. |
| **CPU 오버커밋 비율** | CPU 오버커밋 비율입니다. |
| **메모리 오버커밋 최대 비율** | 남은 할당 가능 메모리를 메모리 회수 허용 인스턴스로 채웠을 때의 비율입니다. 메모리 오버커밋을 끈 노드는 `-`로 표시됩니다. |
| **생성 일시**       | 컴퓨트 노드가 등록된 일시입니다. |

### 상태 이해하기

목록과 상세 화면에 표시되는 컴퓨트 노드 상태는 다음과 같습니다.

| 상태 | 의미 |
| --- | --- |
| **`정상`** | 노드가 정상 동작 중이며 인스턴스를 배치할 수 있습니다. |
| **`이상: 응답 없음`** | 노드가 점검에 한 번 이상 응답하지 않았습니다. 다음 점검에서 응답하면 `정상`으로 돌아갑니다. 약 1분간 계속 응답하지 않으면 노드가 실제로 멈췄는지 확인합니다. 노드가 꺼졌거나 네트워크에서 떨어졌으면 `페일오버 진행 중`으로 바뀝니다. 노드는 살아 있고 호스트 에이전트만 응답하지 않으면 페일오버하지 않고 이 상태로 기다립니다. 이때 인스턴스는 그대로 실행되지만 시작·정지 같은 조작은 할 수 없습니다. 5분이 넘으면 `호스트 에이전트 응답 없음` 이벤트가 발생하니 노드의 호스트 에이전트를 확인합니다. 호스트 에이전트가 다시 연결되면 `정상`으로 돌아갑니다. |
| **`이상: 미정리 인스턴스 있음`** | 장애에서 돌아왔지만 이전 인스턴스 흔적을 아직 다 정리하지 못했습니다. 정리가 끝날 때까지 새 인스턴스를 배치하지 않습니다. |
| **`생성 중`** | 노드가 등록·준비 중입니다. |
| **`삭제 중`** | 노드 삭제가 진행 중입니다. |
| **`페일오버 진행 중`** | 노드 장애가 감지되어 해당 노드의 인스턴스를 다른 노드로 옮기는 작업이 진행 중입니다. |
| **`유지관리 중`** | 점검을 위해 노드를 인스턴스 배치 대상에서 제외한 상태입니다. 인스턴스를 옮기는 중일 때와 옮기기를 마친 뒤 모두 이 상태로 표시되며, 진행 단계는 `물리 머신 > 노드`의 `유지관리 상태`에서 확인합니다. 자세한 내용은 [유지관리 모드](../machine/machine.md#유지관리-모드)를 참고하세요. |
| **`정지됨`** | 노드가 중지되었거나 연결이 끊긴 상태입니다. |
| **`에러`** | 내부 복구 실패 등 오류가 발생한 상태입니다. |

> 💡 **참고:** 호스트 에이전트가 다시 연결되면 `호스트 에이전트 응답 복구` 이벤트가 발생합니다. 이메일·웹훅으로 `호스트 에이전트 응답 없음`을 받았다면 이 복구 이벤트로 해소를 확인합니다. 기다리는 동안 노드가 관리망에서도 응답하지 않아 `페일오버 진행 중`으로 바뀌면 복구 이벤트가 발생하지 않습니다. 이때는 노드 상태를 확인한 뒤, 이메일·웹훅을 받는 쪽에서 해당 알림을 직접 정리합니다.

## 컴퓨트 노드 편집

컴퓨트 노드 편집 화면에서는 노드 이름은 조회만 가능하며, CPU 오버커밋 비율과 메모리 오버커밋 켬/끔을 수정할 수 있습니다.

### 입력 항목

| 항목 | 설명 |
| --- | --- |
| **이름** | 읽기 전용 항목입니다. |
| **CPU 오버커밋 비율** | 슬라이더로 비율을 조정합니다. |
| **메모리 오버커밋** | `활성화`/`비활성화` 토글로 켜거나 끕니다. 토글 옆에 현재 비율이 표시되고, 켠 노드는 최대 비율도 함께 표시됩니다(예: `현재 비율 1.53 · 최대 비율 1.80`). 토글 아래 막대는 할당 가능 메모리 가운데 인스턴스가 예약한 몫을 보이고, 막대 아래 양끝에 `예약`과 `여유`가 표시됩니다. 끌 수 있는지는 현재 비율로 정해집니다. |

노드의 host-agent가 메모리 회수를 지원하지 않으면 토글을 켤 수 없고, 아래에 `이 노드의 host-agent 가 메모리 회수를 지원하지 않아 켤 수 없습니다. host-agent 를 업데이트하세요.`가 표시됩니다. 이 경우 해당 노드의 host-agent를 업데이트한 뒤 다시 시도하세요.

### CPU 오버커밋 비율 규칙

- 설정 범위: **1.00 ~ 2.00**
- 권장 기준: **1.5 이하**
- 기존 값과 동일하면 **저장 버튼이 비활성화**됩니다.
- 오버커밋은 **여러 인스턴스를 한 노드에 겹쳐 얹기 위한 총량 설정**입니다. 인스턴스 하나의 `vCPU`·메모리는 비율과 무관하게 그 노드의 **물리** 자원을 넘을 수 없습니다. 예를 들어 물리 16코어 노드에 비율 2.00을 설정하면 합계 32 vCPU까지 배치할 수 있지만, 24 vCPU짜리 인스턴스 하나는 배치되지 않습니다.
- 이미 배치된 인스턴스의 `vCPU` 합이 새 비율로 계산한 총량보다 크면 변경이 거부됩니다. 먼저 인스턴스를 다른 노드로 옮기세요.

### 메모리 오버커밋 규칙

메모리 오버커밋은 노드마다 켜거나 끕니다. 기본값은 **비활성화**입니다. 비율을 직접 입력하지 않습니다.

| 설정 | 동작 |
| --- | --- |
| **비활성화** | 모든 인스턴스를 설정한 메모리 크기만큼 예약합니다. 인스턴스 메모리 합계에 가상화 오버헤드와 급증 대비 여유를 더한 예약이 할당 가능 메모리를 넘을 수 없습니다. |
| **활성화** | [메모리 회수 허용](../../../project/vm/instance/instance.md#메모리-회수-허용)을 켠 인스턴스는 보장 메모리(메모리 크기의 50%)만 예약합니다. 그만큼 더 많은 인스턴스를 노드에 배치할 수 있습니다. 메모리 회수 허용을 끈 인스턴스는 메모리 크기 전체를 예약합니다. |

- **메모리 오버커밋 최대 비율**은 사람이 정하는 값이 아니라 계산 결과입니다. 노드 목록과 상세 화면에 소수 둘째 자리까지 표시하며, 남은 할당 가능 메모리(할당 가능 메모리에서 인스턴스 예약 메모리를 뺀 값)를 메모리 회수 허용 인스턴스로 채웠을 때 닿는 비율입니다. 새 인스턴스의 가상화 오버헤드는 셈하지 않으므로 실제로 배치하면 조금 낮을 수 있습니다. 메모리 오버커밋을 끈 노드는 `-`로 표시합니다.
- **현재 비율**은 편집 화면의 토글 옆에 표시하며 `인스턴스 메모리 합계 ÷ 할당 가능 메모리`입니다. 최대 비율은 현재 비율보다 작을 수 없습니다.
- 켠 노드의 토글을 끄면 저장하기 전에 막대가 끈 뒤의 예약을 미리 보입니다. 예약은 주황, 늘어날 예약은 연주황으로 칠합니다. 할당 가능 메모리를 넘으면 그 자리에 세로선을 긋고 넘는 몫을 빨강으로 칠하며, 막대 아래 숫자가 `예약 124 GB → 184 GB` 처럼 바뀝니다. 켤 때는 저장한 뒤에 막대가 바뀝니다.
- 인스턴스 예약 메모리(보장 메모리와 가상화 오버헤드의 합)가 할당 가능 메모리 안에 들 때만 새 인스턴스를 배치합니다. 인스턴스 하나의 메모리 크기도 그 노드의 할당 가능 메모리를 넘을 수 없습니다.
- 켜는 즉시 그 노드에 이미 있던 메모리 회수 허용 인스턴스도 보장 메모리만 예약하는 것으로 계산하므로 여유가 생깁니다.
- 끈 뒤의 예약이 할당 가능 메모리를 넘으면 끌 수 없습니다. 토글을 껐을 때 막대에 빨강 구간과 `초과`가 보이는 경우입니다. 현재 비율이 1.00 이하여도 인스턴스 메모리 합계가 할당 가능 메모리에 가까우면 가상화 오버헤드와 급증 대비 여유를 더해 넘을 수 있습니다. 이때 `할당 가능 메모리를 넘어 끌 수 없습니다. 인스턴스를 다른 노드로 옮긴 뒤 끄세요.`가 표시되고 저장할 수 없습니다. 인스턴스를 다른 노드로 옮긴 뒤 다시 끄세요.
- 기존 값과 동일하면 **저장 버튼이 비활성화**됩니다.

> ⚠️ **주의:** 메모리 오버커밋은 노드 메모리가 실제로 모자라는 상황을 완전히 막지는 못합니다. 메모리 회수 허용 인스턴스들이 보장 메모리보다 많은 메모리를 실제로 쓰면 노드가 되찾을 메모리가 없습니다. 이 상태에서 노드 메모리가 바닥나면 그 노드의 인스턴스가 강제로 종료될 수 있습니다. 종료할 인스턴스는 메모리 회수 허용 인스턴스 중에서 먼저 고릅니다. 다만 메모리 회수 허용을 끈 인스턴스 하나가 그 노드의 할당 가능 메모리 대부분을 쓰고 있으면 그 인스턴스가 먼저 종료될 수 있습니다. 강제로 종료된 인스턴스는 자리가 있는 다른 노드에서 다시 시작하고, 다른 노드에 자리가 없으면 같은 노드에서 다시 시작합니다. 메모리 회수 허용 인스턴스가 쓰는 메모리가 갑자기 늘면 회수한 메모리를 돌려주는 동안 일시적으로 느려질 수도 있습니다.
>
> 노드의 메모리 사용이 95% 이상이면 그 노드는 새 인스턴스 배치 대상에서 빠집니다. 메모리 오버커밋을 켠 노드는 다음처럼 운영하세요.
>
> - 메모리를 천천히 쓰거나 대부분 쉬는 인스턴스(개발·시험용 등)에만 메모리 회수 허용을 켭니다.
> - [컴퓨트 대시보드](../../dashboard/compute-dashboard/compute-dashboard.md)에서 노드의 실제 메모리 사용량을 보고, 사용량이 높은 노드의 메모리 회수 허용 인스턴스를 다른 노드로 옮겨 여유를 남깁니다.

### 저장/취소

- **`저장`**: 변경한 오버커밋 설정을 반영하고 목록 화면으로 이동합니다.
- **`취소`**: 변경 사항을 저장하지 않고 목록 화면으로 이동합니다.

## 컴퓨트 노드 상세

컴퓨트 노드 상세 화면은 상단 **정보 영역**과 하단 **탭 정보**로 구성됩니다.
상단 정보 영역은 기본 정보, 상태 정보 두 묶음으로 나뉩니다.

### 기본 정보

| 항목 | 설명 |
| --- | --- |
| **이름** | 컴퓨트 노드 이름입니다. |
| **CPU 오버커밋 비율** | CPU 오버커밋 비율입니다. |
| **메모리 오버커밋 최대 비율** | 남은 할당 가능 메모리를 메모리 회수 허용 인스턴스로 채웠을 때의 비율입니다. 메모리 오버커밋을 끈 노드는 `-`로 표시합니다. |
| **인스턴스 수** | 노드에 배치된 인스턴스의 수입니다. |
| **생성 일시** | 컴퓨트 노드 생성 일시입니다. |

### 상태 정보

| 항목 | 설명 |
| --- | --- |
| **상태** | 컴퓨트 노드 운영 상태입니다. |
| **Agent 연결 상태** | Host Agent 연결 상태를 표시합니다. |
| **네트워크 상태** | 네트워크 점검 결과를 표시합니다. |
| **가상화 연결 상태** | 노드의 가상화 계층 연결 상태를 표시합니다. |

#### 연결 상태 값

`Agent 연결 상태`, `네트워크 상태`, `가상화 연결 상태`는 다음 값으로 표시됩니다.

| 구분 | 값 | 의미 |
| --- | --- | --- |
| **가상화 연결 상태** | `연결` | 노드의 가상화 계층과 정상적으로 연결되어 있습니다. |
| | `해제` | 노드에는 연결되지만 가상화 계층이 응답하지 않습니다. |
| | `도달 불가` | 노드에 확인을 요청했으나 응답이 오지 않았습니다. |
| | `알 수 없음` | 연결 상태를 확인할 수 없습니다. |
| **Agent 연결 상태** | `연결` | Host Agent와 정상적으로 연결되어 있습니다. |
| | `해제` | Host Agent 연결이 끊겼습니다. |
| **네트워크 상태** | `정상` | 내부망과 외부망 점검이 모두 정상입니다. |
| | `내부만 정상` | 내부망 점검은 정상이고 외부망 점검은 정상이 아닙니다. |
| | `외부만 정상` | 외부망 점검은 정상이고 내부망 점검은 정상이 아닙니다. |
| | `에러` | 네트워크 점검이 정상이 아닙니다. |
| | `알 수 없음` | 네트워크 상태를 확인할 수 없습니다. |

`네트워크 상태`가 `정상`이 아니거나 `가상화 연결 상태`가 `연결`이 아니면 값 아래에 원인이 회색 글씨로 함께 표시됩니다. 상태가 정상으로 돌아오면 원인 표시는 사라집니다.

### 탭 구성

#### 리소스

CPU와 메모리를 막대로 보여 줍니다. 막대 구간에 마우스를 올리거나 키보드로 옮기면 구간 이름과 값이 표시됩니다. 막대 오른쪽에는 값과 할당률이 표시됩니다.

| 항목 | 설명 |
| --- | --- |
| **논리 CPU 수** | 할당된 논리 CPU(보라)와 미할당(회색) 막대입니다. 값은 `할당 / 전체`(예: `60 / 96개`)이고 아래에 할당률이 표시됩니다. |
| **할당 가능 메모리** | 노드 전체 메모리에서 시스템 예약을 뺀, 인스턴스가 쓸 수 있는 메모리입니다. 값 옆에 `= 전체 512 GB − 시스템 예약 32 GB`처럼 계산 내역이 표시됩니다. 두 메모리 막대에는 이 값 자리에 세로 경계선이 그어집니다. |
| **인스턴스 예약 메모리** | 보장 메모리(진보라)와 가상화 오버헤드(연보라)의 합입니다. 경계선까지 남은 회색 구간이 배치 가능 여유입니다. 값은 `예약 / 할당 가능`이고 아래에 할당률이 표시됩니다. 할당 가능 메모리를 넘으면 막대가 경계선 밖으로 나가고, 초과량과 함께 `새 인스턴스 배치 불가`가 표시됩니다. 이 값이 할당 가능 메모리 안에 들 때만 새 인스턴스를 배치합니다. |
| **인스턴스 메모리 합계** | 인스턴스에 설정한 메모리 크기의 합입니다. 막대는 게스트 실사용·현재 크기 중 미사용·회수 중(빗금)으로 나뉩니다. 회수 중을 뺀 현재 크기가 경계선 안에 드는지 볼 수 있습니다. 값 옆에 현재 비율(`인스턴스 메모리 합계 ÷ 할당 가능 메모리`)이 붙고, 메모리를 회수 중인 인스턴스가 있으면 값 아래에 `회수 중 52 GB · 인스턴스 5대`가 표시됩니다. |
| **수정 일시** | 리소스 정보 마지막 갱신 시각입니다. |

두 메모리 막대는 같은 눈금입니다. 할당 가능 메모리가 집행되지 않는 노드는 `미적용 — 새 인스턴스 배치 불가 (사유)`로 표시하고, 경계선 없이 물리 메모리를 눈금으로 그립니다.

#### 모니터링

모니터링 탭에서는 이 노드 위의 인스턴스가 CPU를 얼마나 기다렸는지 보여줍니다. 왼쪽 위의 기간 선택으로 조회 기간을 바꾸면 그래프와 목록이 모두 그 기간을 기준으로 갱신됩니다.

달력 오른쪽 드롭다운에서 그래프를 자동으로 다시 읽는 주기를 `꺼짐`, `30초`, `1분`, `5분` 중에서 고릅니다(기본 `30초`). 켜 두면 주기마다 조회 기간의 끝을 지금으로 옮겨 갱신하고, 기간을 직접 고르면 `꺼짐`으로 바뀝니다. 그 오른쪽의 `새로고침` 버튼을 클릭하면 주기를 기다리지 않고 바로 갱신합니다.

> 💡 **참고:** 노드의 CPU 사용률 같은 자원 사용량은 이 탭이 아니라 `물리 머신 > 노드` 상세의 [모니터링](../machine/machine.md#모니터링) 탭에서 확인합니다. `물리 머신 > 노드`의 모니터링은 노드의 자원 사용량을, 이 탭은 인스턴스가 겪는 상태를 보여줍니다.

**인스턴스 CPU 대기율** 그래프는 인스턴스의 vCPU가 실행되려고 물리 CPU를 기다린 시간의 비율(%)입니다. 5% 이상이면 인스턴스가 느려질 수 있습니다. 그래프 제목 옆 안내 아이콘에 마우스를 올리면 같은 설명이 표시됩니다.

| 그래프 선 | 설명 |
| --- | --- |
| **vCPU 가중 평균** (진한 선) | 구간마다 인스턴스별 대기율을 vCPU 수로 가중해 평균한 선입니다. 노드 전체가 얼마나 밀리는지 보여줍니다. |
| **최대** (같은 색 옅은 선) | 구간마다 인스턴스별 대기율을 구해, 그중 가장 높은 값을 이은 선입니다. |

그래프 위에 마우스를 올리면 그 시각의 두 값이 표시되고, 그 자리를 클릭하면 값 상자가 고정됩니다. `Esc` 키를 누르거나 조회 기간·창 크기를 바꾸면 풀립니다.

조회 기간이 길수록 그래프 한 점이 나타내는 구간이 1분, 5분, 1시간으로 넓어집니다. 그래프의 **최대**는 구간 평균을 기준으로 한 값이므로, 기간이 길면 잠깐 치솟은 경합이 낮게 보일 수 있습니다. 순간의 최고치는 아래 목록의 **최대 대기율**에서 확인합니다.

**대기 상위 인스턴스** 목록은 조회 기간의 평균 대기율이 높은 순서대로 인스턴스를 최대 10개까지 보여줍니다. 페이지는 나누지 않습니다.

| 컬럼 | 설명 |
| --- | --- |
| **이름** | 인스턴스 이름입니다. |
| **프로젝트** | 인스턴스가 속한 프로젝트입니다. |
| **vCPU** | 인스턴스에 할당된 vCPU 수입니다. |
| **CPU 사용률** | 조회 기간의 평균 CPU 사용률입니다. |
| **평균 대기율** | 조회 기간의 평균 대기율입니다. |
| **최대 대기율** | 조회 기간 중 가장 높았던 대기율입니다. |

값을 구할 수 없는 칸은 `-`로 표시됩니다.

##### 대기율이 높을 때

**확인 순서**

1. 일시적인지 계속되는지 봅니다. 예를 들어 30분 이상 이어지면 계속되는 것으로 봅니다.
2. 노드 전체가 밀리는지, 일부 인스턴스만 밀리는지 봅니다. **vCPU 가중 평균**도 높으면 노드 전체가 밀리는 것이고, **최대**만 높으면 일부 인스턴스의 문제입니다.
3. 노드 CPU 사용률과 인스턴스별 CPU 사용률을 함께 봅니다. 노드 CPU 사용률은 `물리 머신 > 노드`의 모니터링 탭에서, 인스턴스별 사용률은 위 목록의 **CPU 사용률**에서 확인합니다.
   - 사용률이 높고 대기도 높으면 바쁜 인스턴스가 CPU를 충분히 받지 못하는 것입니다.
   - 사용률이 낮은데 대기가 높으면 이웃한 인스턴스 때문에 손해를 보는 것입니다.
   - Ceph OSD처럼 노드 자체에서 도는 프로세스가 CPU를 쓰고 있을 수도 있습니다.

**조치**

- 인스턴스를 다른 노드로 라이브 마이그레이션합니다. 자세한 내용은 [인스턴스 마이그레이션](#인스턴스-마이그레이션)을 참고하세요.
- CPU 오버커밋 비율을 낮춥니다. 권장은 1.5배 이내입니다. 이미 배치된 vCPU 합이 새 총량보다 크면 변경이 거부되므로 인스턴스를 먼저 다른 노드로 옮깁니다. 자세한 내용은 [CPU 오버커밋 비율 규칙](#cpu-오버커밋-비율-규칙)을 참고하세요.
- 사용률에 비해 vCPU가 큰 인스턴스는 vCPU를 줄이도록 권고합니다.
- 노드를 증설합니다.

### 인스턴스 우선순위

우선순위는 노드에 문제가 생겼을 때 어떤 인스턴스를 먼저 챙길지 정하는 값입니다. 관리자만 보고 바꿀 수 있으며, 프로젝트 사용자에게는 보이지 않습니다.

| 상황 | 순서 |
| --- | --- |
| 장애로 다른 노드에서 다시 켤 때 | 우선순위가 높은 인스턴스부터 켭니다. |
| 유지관리 모드로 노드를 비울 때 | 우선순위가 높은 인스턴스부터 옮깁니다. |
| 노드 메모리가 부족해 [메모리 회수 허용](../../../project/vm/instance/instance.md#메모리-회수-허용) 인스턴스의 메모리를 거둘 때 | 우선순위가 낮은 인스턴스에서 먼저 더 거둘 수 있습니다. 메모리가 크게 부족하면 모든 인스턴스를 똑같이 거둡니다. |
| 노드 메모리가 부족해 인스턴스를 종료해야 할 때 | 우선순위가 낮은 인스턴스를 먼저 고릅니다. |

- 새로 만든 인스턴스는 `보통`입니다. 파일 시스템·패키지 미러·컨테이너 레지스트리 인스턴스는 `시스템`으로 고정되어 가장 먼저 챙기며, 바꿀 수 없습니다.
- 우선순위는 순서를 정할 뿐입니다. `높음`인 인스턴스도 종료될 수 있습니다.
- CPU·디스크 성능에는 영향을 주지 않습니다.

**우선순위 바꾸기**

1. 인스턴스 탭에서 바꿀 인스턴스를 체크박스로 고릅니다. 한 번에 1~20개까지 고를 수 있습니다.
2. **`우선순위 변경`** 버튼을 클릭합니다.
3. `높음`·`보통`·`낮음` 중 하나를 고릅니다. 창 아래 `변경 대상` 표의 `변경 후` 칸에서 바뀔 결과를 미리 볼 수 있습니다.
4. **`변경`**을 클릭합니다.

고른 인스턴스의 우선순위가 서로 다르면 창이 열릴 때 아무 단계도 골라져 있지 않습니다. `시스템` 인스턴스는 바뀌지 않고 아래 `변경할 수 없는 인스턴스` 표에 따로 표시됩니다. 이미 고른 단계인 인스턴스는 `변경 없음`으로 표시됩니다. `시스템` 인스턴스만 고르면 버튼이 비활성화됩니다.

### 인스턴스 마이그레이션

인스턴스 탭에서 옮길 인스턴스를 체크박스로 고릅니다. 한 번에 1~20개까지 고를 수 있고, 페이지를 넘겨도 선택이 유지됩니다. 고른 뒤 **`마이그레이션`** 버튼을 클릭하면 2단계 마법사(`목적지 지정` → `계획 확인`)가 열립니다. 한 개만 골라도 같은 마법사를 씁니다.

**`마이그레이션`** 버튼은 다음 경우에 비활성화되며, 마우스를 올리면 이유가 표시됩니다.

- 고른 인스턴스가 없을 때: `선택된 항목이 없습니다.`
- 21개 이상 골랐을 때: `인스턴스 최대 20개까지 선택할 수 있습니다.`
- 마이그레이션 중이거나 대기 중인 인스턴스가 포함됐을 때: `마이그레이션 중이거나 대기 중인 인스턴스가 있습니다.`

마이그레이션 방식은 두 가지입니다.

- **`라이브`**: 인스턴스를 켜 둔 채로 다른 컴퓨트 노드로 옮깁니다.
- **`콜드`**: 인스턴스를 종료한 뒤 대상 노드에서 다시 시작합니다.

라이브 마이그레이션 데이터는 기본 설정에서 내부망으로 전송합니다. 두 노드 중 한쪽에 내부망 주소가 없으면 목록에서 그 노드로 가는 라이브를 막고 `두 노드 사이에 마이그레이션 경로가 없음 (콜드 마이그레이션만 가능)`을 표시합니다. 콜드로 옮기거나, 내부망 주소가 없는 노드의 주소 설정과 연결을 점검한 뒤 다시 시도합니다.

한 노드가 동시에 보내거나 받는 라이브 마이그레이션 수는 그 노드의 링크 속도(기본 설정에서는 내부망)로 정합니다. 1Gbps 는 1건, 10Gbps 는 2건, 25Gbps 는 5건, 40Gbps 이상은 8건이고, 속도를 확인하지 못하면 1건입니다. 한도를 넘는 요청은 거절하지 않고 같은 줄에서 순서대로 기다렸다가 시작하며, 최대 2시간 안에 시작하지 못하면 취소합니다. 기다리는 인스턴스는 인스턴스 목록의 상태 칸에 `마이그레이션 대기 · n번째` 로 보입니다. 받는 쪽이 가득 찬 대상 노드 대신 여유 있는 노드를 고르면 기다리지 않고 바로 시작할 수 있습니다.

라이브 마이그레이션 속도는 데이터를 보내는 링크 속도(기본 설정에서는 내부망)에 따라 정해지고, 같은 링크를 쓰는 다른 트래픽(테넌트 네트워크, 내부망에 있는 NFS 스토리지 등)과 나눠 쓰므로 붐비면 느려집니다. 인스턴스에 할당한 메모리가 아래보다 크면 제한 시간 안에 끝나지 않을 것으로 보아 라이브 마이그레이션 대상에서 빼고 콜드 마이그레이션만 허용합니다.

| 링크 속도(기본 설정에서는 내부망) | 라이브 마이그레이션이 가능한 할당 메모리(기본 설정에서 두 노드의 링크 중 느린 쪽 기준) |
| --- | --- |
| 1Gbps | 약 55GiB 까지 |
| 10Gbps | 약 134GiB 까지 |
| 속도를 확인하지 못함 | 약 30GiB 까지 |

표의 크기는 메모리를 많이 고쳐 쓰지 않는 인스턴스를 기준으로 합니다. 인스턴스가 메모리를 고쳐 쓰는 양에 따라 다음과 같이 달라집니다.

- **쓰기가 적은 인스턴스**(웹·애플리케이션 서버 등): 표의 크기까지 제한 시간 안에 끝납니다.
- **쓰기가 많은 인스턴스**(바쁜 데이터베이스·캐시 등): 1Gbps 링크에서는 약 40GiB 이하일 때만 제한 시간 안에 끝날 수 있습니다. 더 크면 쓰기가 적은 시간대에 옮기거나 콜드 마이그레이션을 씁니다. 10Gbps 링크에서는 대체로 표의 크기까지 끝납니다.
- **쓰기가 아주 많은 인스턴스**: 링크 속도와 크기에 상관없이 끝나지 않을 수 있습니다. 콜드 마이그레이션으로 옮깁니다.

라이브 마이그레이션이 제한 시간 안에 끝나지 않으면 취소합니다(전송이 멈추면 몇 분, 전송이 이어지면 최대 약 25분 뒤). 인스턴스는 원래 노드에서 그대로 실행됩니다. 노드 유지관리 모드의 대피 중이면 같은 대상 노드로 콜드 마이그레이션해 옮기므로 인스턴스가 잠시 중단됩니다.

#### 1단계 `목적지 지정`

행마다 목적지와 방식을 정하는 단계입니다. 처음에는 **자동 배치**가 모든 행의 목적지와 방식을 골라 둡니다. 라이브로 갈 수 있는 노드 중 여유 메모리가 가장 큰 노드를 먼저 고르고, 없으면 콜드로 갈 수 있는 노드를 고릅니다. 앞 순서의 인스턴스에 배정한 몫은 여유에서 뺍니다. 이 순서로 배정해 어느 노드가 넘치면, 직접 고른 행은 그대로 두고 나머지를 메모리가 큰 인스턴스부터 다시 배정합니다. 그래도 넘칠 때만 부족 안내가 나옵니다.

창 제목은 `마이그레이션 — <출발 노드 이름>`입니다. 화면은 위에서부터 `목적지별 배정`, `인스턴스` 표, `옮길 수 없음` 표 순서로 보이고, 자원이 부족하면 `진행 불가` 상자가 `목적지별 배정` 아래에 나타납니다.

- **`목적지별 배정`**: 이 계획으로 인스턴스를 받는 노드마다 받는 인스턴스 건수와 그 vCPU·메모리 합이 `<n>건 · <vCPU 합> vCPU · <메모리 합>`으로 표시됩니다. 노드에 남는 양은 아래 막대로 봅니다. 노드 이름 옆에는 그 노드가 받는 링크 속도(`<n> Gbps`)가 흐린 글자로 함께 보이며, 링크 속도를 알 수 없는 노드는 생략됩니다. 노드의 자원이 부족하면 빨간 점과 함께 `<n>건 · 메모리 <값> 부족` 또는 `<n>건 · vCPU <n>개 부족`으로 바뀝니다.
  - 노드마다 `vCPU`·`메모리` 막대가 함께 보입니다. 회색은 지금 쓰는 양, 주황은 이번 마이그레이션으로 늘어나는 양이고, 같은 노드로 이미 대기 중인 다른 마이그레이션이 있으면 그 몫은 줄무늬로, 할당 가능을 넘는 부분은 빨강으로 표시됩니다. 막대 오른쪽 숫자는 `현재 → 완료 후 / 할당 가능`입니다(메모리는 GB).
- **`진행 불가`**: 부족한 노드가 있을 때만 노란 상자로 나타납니다. 부족한 노드와 자원마다 `<노드 이름> 메모리 <값> 부족`(또는 `vCPU <n>개 부족`)과 `<n>건 필요 <값> · 남음 <값>`이 표시되고, 그 아래에 해야 할 일이 한 줄로 안내됩니다. `필요`는 이 마이그레이션 요청만의 양이고, `남음`은 같은 노드로 가려고 이미 대기 중인 다른 마이그레이션 몫을 뺀 양입니다.
  - 어느 노드를 써도 전체 자원이 모자라면 `후보 노드 전체 메모리 <값> 부족 · 목록에서 1건 이상 삭제 필요`(vCPU 는 `후보 노드 전체 vCPU <n>개 부족`)가 나옵니다. 목적지를 바꿔서는 풀리지 않으므로, 목적지를 직접 고른 행이 있어도 이 안내가 먼저 나옵니다. 인스턴스를 목록에서 삭제해 해결합니다.
  - 목적지를 직접 고른 행이 원인이면 `목적지 변경 필요: <인스턴스 이름>, ...`이 나오고 이름을 누르면 해당 행으로 이동합니다. 이때 **`자동 배치`** 버튼이 함께 나옵니다.
  - 일부 노드에 배정이 몰려 부족하면 `<부족한 노드 이름> 배정분 일부 목적지 변경 필요`와 그 아래 `여유 있는 노드: <노드 이름>`이 나옵니다. 여유 있는 노드는 부족한 노드로 가는 인스턴스를 그 인스턴스의 방식(라이브·콜드)으로 실제로 받을 수 있는 노드만 안내합니다.
  - 부족한 노드로 가는 인스턴스를 받을 수 있는 다른 노드가 없으면 `여유 있는 노드 없음 · 목록에서 1건 이상 삭제 필요`가 나옵니다.
  - **`자동 배치`**를 눌러도 부족하면 상자 안에 **`되돌리기`**가 나옵니다.
- **`자동 배치`** 알림: **`자동 배치`** 로 부족이 풀리면 파란 상자에 `자동 배치 · 목적지 <n>건 변경`이 표시됩니다. **`변경 보기`**를 누르면 `인스턴스 · 이전 노드 · → 새 노드` 목록이 펼쳐지고 버튼이 **`변경 접기`**로 바뀝니다. **`되돌리기`**를 누르면 자동 배치를 누르기 직전의 목적지와 방식으로 돌아갑니다. 행을 직접 다시 고치면 이 알림은 사라집니다.

`인스턴스` 표에서 행을 고칩니다.

| 열 | 설명 |
| --- | --- |
| 삼선 핸들 | 행을 끌어 요청 순서를 바꿉니다. 한 개만 옮길 때는 표시되지 않습니다. |
| **순서** | 요청하는 순서입니다. 한 개만 옮길 때는 표시되지 않습니다. |
| **인스턴스** | 인스턴스 이름과 `vCPU · 메모리` 사양입니다. |
| **프로젝트** | 인스턴스가 속한 프로젝트입니다. |
| **목적지** | 받을 노드를 고르는 드롭다운입니다. 항목은 노드 이름만 표시되고, 고를 수 없는 노드는 비활성화되어 `노드 이름 (사유)`로 표시됩니다. 고를 수 있는 노드가 먼저, 그다음 링크 속도가 빠른 순서, 이름 순서로 나열됩니다. |
| **방식** | `라이브` 또는 `콜드`를 고르는 드롭다운입니다. 고른 목적지가 라이브를 받지 못하면 `라이브 불가`가 비활성화되어 `콜드`만 고를 수 있습니다. 시스템이 자동으로 `콜드`로 정한 행에는 드롭다운 아래에 작은 글씨로 `라이브 불가: <사유>`가 표시됩니다. 열 이름 옆 안내 아이콘에 마우스를 올리면 링크 속도별로 라이브가 되는 메모리 크기를 볼 수 있습니다. |
| **예상 시간** | 라이브만 `약 20초`처럼 표시됩니다. 바로 시작하지 못하면 예상 시간 아랫줄에 파란 점과 함께 `대기 1번째`처럼 대기 순번이 따로 표시됩니다. 콜드는 비어 있습니다. |
| **확인 필요** | 이 행의 목적지 노드 자원이 부족하면 `메모리 부족` 또는 `vCPU 부족`, 콜드로 옮기면 `다운타임`이 표시됩니다. 문제가 없으면 비어 있습니다. 목적지 노드의 자원이 부족한 행은 배경이 붉게 표시됩니다. |
| ✕ | 이 행을 목록에서 삭제합니다. 한 개만 옮길 때는 표시되지 않습니다. |

- 목적지나 방식을 바꾸거나 행을 삭제하거나 순서를 바꾸면 계획을 다시 계산합니다. 계산하는 동안 `계획을 다시 계산하는 중입니다`가 표시되고 `다음`이 잠시 비활성화됩니다.
- 목적지 목록에는 **인스턴스가 속한 노드 그룹의 컴퓨트 노드가 현재 노드만 빼고 모두** 나옵니다. 라이브와 콜드가 둘 다 불가인 노드만 선택할 수 없고, 라이브만 불가인 노드는 콜드로 옮길 수 있으므로 선택할 수 있습니다.
- 방식을 직접 고르지 않은 행은 라이브를 받지 못하는 노드를 목적지로 고를 때 방식이 `콜드`로 바뀝니다.
- 방식을 직접 `라이브`로 고르면 라이브를 받지 못하는 노드는 `목적지` 목록에서 비활성화됩니다. 직접 고른 방식은 마법사가 바꾸지 않습니다.
- 마법사를 여는 사이 다른 곳으로 옮겨졌거나 삭제된 인스턴스는 `이 노드에 없음`으로 `옮길 수 없음` 목록에 나오고, 나머지 인스턴스는 그대로 계획됩니다.
- 마법사를 여는 사이 이미 마이그레이션 대기열에 들어간 인스턴스는 `이미 대기 중`으로 `옮길 수 없음` 목록에 나옵니다. 대기가 끝나기를 기다리거나 인스턴스 탭에서 대기를 취소한 뒤 다시 요청합니다.
- 어느 노드로도 옮길 수 없는 인스턴스는 표 아래 `옮길 수 없음` 표(인스턴스 · 프로젝트 · 사유)에 따로 모입니다. 인스턴스가 `실행 중`이 아니라서 옮기지 못하면 사유 칸에 인스턴스 목록과 같은 상태(예: `정지됨`)가 표시되고, 노드 때문에 옮기지 못하면 같은 사유의 노드를 한 줄로 묶어 `노드 이름, 노드 이름: 사유` 형식으로 표시합니다. 이 인스턴스는 요청에 들어가지 않습니다. 사유별 조치는 [자주 나타나는 차단 사유](#자주-나타나는-차단-사유)를 참고하세요.
- 목적지의 자원이 부족하게 배정되면 `다음`과 단계 머리글 `계획 확인`이 비활성화되고, 마우스를 올리면 `<노드 이름> 자원 부족` 형식의 이유가 보입니다. `진행 불가` 상자의 안내에 따라 **`자동 배치`**를 누르거나 목적지를 바꾸거나 행을 삭제해 해결합니다.
- 라이브로 옮길 인스턴스가 대기열의 남은 자리보다 많으면 `다음`이 비활성화되고, 마우스를 올리면 `대기열에 남은 자리가 n건이라 라이브 m건을 모두 요청할 수 없습니다. 라이브 건수를 줄이거나 나누어 요청하세요.`가 표시됩니다. 안내 상자는 나오지 않습니다.
- 계획을 계산하지 못했거나(`계획을 계산하지 못했습니다.`) 옮길 인스턴스가 하나도 없을 때(`옮길 인스턴스가 없습니다.`)도 `다음`이 비활성화되고 이유가 표시됩니다. 계산하지 못했을 때는 안내 상자 오른쪽에 **`다시 계산`** 버튼이 나옵니다. 창을 닫지 않고 이 버튼으로 다시 계산합니다.

#### 2단계 `계획 확인`

정한 계획을 한 번 더 확인하는 단계입니다. 여기서는 바꿀 수 없으며, 고치려면 `이전`으로 돌아갑니다.

- **`마이그레이션 영향`**: 콜드로 옮기는 인스턴스가 있으면 노란 상자에 `콜드 n건 · 이동 중 중지`와 해당 인스턴스 이름이 한 줄에 하나씩 표시됩니다.
- **경고**: 2시간 안에 시작하지 못할 것으로 보이는 인스턴스가 있으면 노란 상자에 `2시간 내 시작 불가 예상 n건`이 표시됩니다.
- **`계획 확인`**: `라이브 n건`, `콜드 n건`, `옮길 수 없음 n건`, `예상 시간 약 <시간>`이 항목별로 표시됩니다. `옮길 수 없음`은 있을 때만, `예상 시간`은 라이브가 있을 때만 나오며 라이브 전체의 예상 시간입니다.
- **`목적지별 배정`**: 1단계와 같은 모양으로 노드별 건수와 `vCPU`·`메모리` 막대가 표시됩니다.
- **`순서`** 표: 요청 순서대로 순서 · 인스턴스(이름과 vCPU·메모리) · 프로젝트 · 목적지 · 방식 · 시작 · 예상 시간이 표시됩니다. `시작`은 바로 시작하면 `바로`, 기다려야 하면 `약 <시간> 후`와 그 아래 `n번 완료 후`(또는 `다른 요청 완료 후`)가 표시됩니다.
- **`옮길 수 없음`** 표: 옮길 수 없는 인스턴스와 사유가 있을 때만 나옵니다(1단계와 같은 모양).

확인 버튼 **`마이그레이션 N건`**의 N 은 실제로 요청하는 인스턴스 수이며 `옮길 수 없음`은 빠집니다. 버튼을 클릭하면 인스턴스를 목록 순서대로 하나씩 요청하고 창이 닫힙니다. 요청한 인스턴스는 목록의 선택에서 빠집니다. 접수가 거절된 인스턴스가 있어도 나머지는 계속 요청합니다. 한 대도 접수되지 않으면 창이 닫히지 않고 남습니다. 알림의 사유를 확인하고 고쳐서 다시 요청합니다. 요청하지 않고 나가려면 1단계에서 **`취소`**를 클릭해 창을 닫습니다.

> ⚠️ **주의:** 콜드 마이그레이션은 인스턴스를 종료했다가 다시 시작하므로 그동안 서비스가 중단됩니다. 이 마법사에는 별도의 동의 상자가 없고 `마이그레이션 N건` 버튼을 누르는 것이 곧 동의입니다. 누르기 전에 요약의 `콜드` 건수와 각 행의 방식을 확인합니다. 자동 배치나 목적지 변경으로 방식이 `콜드`가 될 수 있습니다.

#### 대기와 취소

라이브 마이그레이션은 한 노드가 동시에 보내거나 받을 수 있는 건수가 정해져 있습니다. 이 건수를 넘는 요청은 거절하지 않고 기다렸다가 순서대로 시작합니다. 콜드는 기다리지 않고 바로 시작합니다.

- 같은 노드로 보내거나 받으려고 기다리는 라이브는 요청한 순서대로 시작합니다. 이미 기다리는 요청이 있으면 그 뒤에 서며, 앞 요청이 기다리는 노드와 겹치지 않는 요청은 앞 요청보다 먼저 시작할 수 있습니다.
- 대기 중인 인스턴스는 인스턴스 목록의 `상태` 칸에 파란 점과 `마이그레이션 대기 · n번째`로 표시됩니다. 상태 옆 안내 아이콘에 마우스를 올리면 목적지 노드와 기한(`→ <노드 이름> · <일시>까지 대기`)이 나옵니다. 대기 중에는 인스턴스가 원래 노드에서 그대로 실행됩니다.
- 옮기는 중인 라이브 마이그레이션은 노란 점과 `마이그레이션 중 n%`로 표시되고, 안내 아이콘에 목적지와 남은 메모리, 경과 시간이 나옵니다. 진행률을 알 수 없으면 `마이그레이션 중`만 표시됩니다.
- 2시간 안에 시작하지 못한 대기는 취소됩니다.

대기 중인 요청은 **`대기 취소`**로 바로 취소합니다.

1. 인스턴스 탭에서 대기 중인 인스턴스를 고릅니다.
2. **`대기 취소`** 버튼을 클릭합니다.

- 확인 창 없이 바로 취소되고 알림이 표시됩니다. 취소한 인스턴스는 다시 마이그레이션을 요청하면 됩니다.
- 대기 중인 인스턴스만 골랐을 때 버튼이 활성화됩니다. 고른 인스턴스가 없으면 비활성화되고 `선택된 항목이 없습니다.`가, 대기 중이 아닌 인스턴스가 섞여 있으면 `마이그레이션 대기 중인 인스턴스만 고르세요.`가 표시됩니다.
- 취소하는 사이에 이미 시작된 인스턴스는 취소되지 않습니다. 일부만 취소됐으면 알림에 취소한 건수와 실패한 인스턴스 이름이 표시됩니다.

#### 결과 알림

여러 대를 요청하면 알림이 두 번 나옵니다.

1. 요청이 접수되면 `마이그레이션 n건을 요청했습니다.`가 표시됩니다.
2. 모든 요청이 끝나면 결과 알림 하나가 표시됩니다.
   - 모두 성공하면 `마이그레이션 n건 중 n건 완료`입니다.
   - 실패한 건이 있으면 `마이그레이션 n건 중 a건 완료, b건 실패: <이름>, <이름>`처럼 완료·실패 건수와 실패한 인스턴스 이름을 보여 줍니다.

- 접수가 거절된 인스턴스는 요청 직후에 `마이그레이션 n건을 요청하지 못했습니다.` 알림이 먼저 나옵니다. 알림에는 거절 사유별로 `<이름>, <이름>: <사유>` 줄이 나오고, 같은 사유는 한 줄로 묶입니다. 한 대도 접수되지 않았다면 이 알림만 나오고 결과 알림은 나오지 않습니다. 이 인스턴스와 2시간 안에 시작하지 못해 취소된 대기는 결과 알림에서 실패로 셉니다.
- `대기 취소`로 취소한 인스턴스는 전체 건수에는 들어가지만 완료에도 실패에도 세지 않습니다. 그래서 `마이그레이션 4건 중 3건 완료`처럼 완료 건수가 전체보다 적은데 실패는 표시되지 않을 수 있습니다. 모두 취소하면 결과 알림이 나오지 않습니다.
- 결과 알림은 모든 요청이 끝난 뒤에 나오므로 대기하는 인스턴스가 있으면 늦게 나옵니다. 진행 상황은 인스턴스 목록의 `상태` 칸에서 확인합니다.
- 화면이 요청마다 결과를 확인하는 시간은 최대 3시간이며, 대기 기한(2시간 안에 시작하지 못하면 취소)과는 별개입니다. 이 시간 안에 결과를 확인하지 못한 건은 알림에 실패로 표시되므로 `상태` 칸을 함께 확인합니다.
- 한 개만 요청하면 그 인스턴스의 요청·완료 알림이 각각 표시됩니다.

#### 자주 나타나는 차단 사유

이 사유들은 `목적지` 목록(`노드 이름 (사유)`), `옮길 수 없음` 표에 표시됩니다. `목적지` 목록의 사유는 그 노드를 고를 수 없는 이유이고, 시스템이 자동으로 `콜드`로 정한 행의 방식 아래 사유는 `라이브`만 막는 이유입니다.

| 화면에 표시되는 사유 | 막히는 곳 | 확인·조치 |
| --- | --- | --- |
| `호스트가 UP 상태가 아님` | 목적지 | 대상 노드 상태가 `정상`이 아닙니다. 다른 노드를 고르거나, 노드가 `정상`이 된 뒤 다시 시도합니다. |
| `이 인스턴스의 매체 스토리지를 공유하지 않음` | 목적지 | 대상 노드가 인스턴스 디스크가 있는 스토리지 도메인을 보지 못합니다. 해당 스토리지를 공유하는 노드를 고릅니다. |
| `마운트된 ISO 를 공유하지 않음 (ISO 해제 후 마이그레이션 가능)` | 목적지 | 디스크는 공유되지만 마운트된 ISO만 대상 노드에 없습니다. `ISO 해제`로 CD/DVD 의 ISO 를 해제한 뒤 다시 시도합니다. `실행 중`에도 해제할 수 있습니다. |
| `필요한 스토리지 도메인에 연결되지 않음` | 목적지 | 대상 노드 상세의 **스토리지 도메인** 탭에서 `접근 상태` 값을 확인합니다. |
| `vCPU 여유 부족` | 목적지 | 대상 노드의 vCPU 여유가 모자랍니다. 다른 노드를 고르거나 대상 노드의 인스턴스를 정리합니다. |
| `메모리 여유 부족` | 목적지 | 대상 노드의 여유 메모리가 모자랍니다. 다른 노드를 고르거나 **`자동 배치`**를 누르거나 대상 노드의 인스턴스를 정리합니다. |
| `이 인스턴스가 사용하는 장치가 호스트에 없음` | 목적지 | 인스턴스가 사용하는 장치를 갖춘 노드를 고릅니다. |
| `인스턴스 선호도 규칙이 이 호스트를 허용하지 않음` · `호스트 선호도 규칙이 이 호스트를 허용하지 않음` | 목적지 | 강제 적용 중인 선호도 규칙이 이 노드를 막고 있습니다. 규칙이 허용하는 노드를 고르거나 규칙을 조정합니다. |
| `노드의 CPU 정보를 확인할 수 없음` | 목적지 | 노드의 CPU 정보를 아직 받지 못했습니다. 노드 상태가 `정상`인지 확인하고 잠시 뒤 다시 시도합니다. |
| `두 노드 사이에 마이그레이션 경로가 없음 (콜드 마이그레이션만 가능)` | `라이브` 방식 | 한쪽 노드에 내부망 주소가 없어 라이브 데이터를 보낼 수 없습니다. `콜드`로 옮기거나, 내부망 주소가 없는 노드의 주소 설정과 연결을 점검합니다. |
| `현재 호스트와 CPU 비호환` | `라이브` 방식 | 콜드 마이그레이션은 재기동이라 CPU 차이의 영향을 받지 않습니다. `콜드`로 옮깁니다. |
| `할당 메모리가 라이브 한도를 넘음 (콜드 마이그레이션만 가능)` | `라이브` 방식 | 인스턴스 메모리가 커서 라이브 마이그레이션이 제한 시간 안에 끝나지 않을 것으로 보입니다. 콜드 마이그레이션으로 옮기거나, 더 빠른 망으로 연결된 노드를 고르세요. |
| `보안 인스턴스는 라이브 마이그레이션 미지원` | `라이브` 방식 | 보안 유형이 `SEV`, `SEV-ES`, `SEV-SNP`인 인스턴스는 `콜드`로만 옮길 수 있습니다. |
| `가속기(GPU/NPU) 패스스루 인스턴스는 라이브 마이그레이션 미지원` | `라이브` 방식 | GPU·NPU를 직접 연결한 인스턴스는 `콜드`로만 옮길 수 있습니다. |

> 💡 **참고:** `유지관리 중`인 노드도 `목적지` 목록에 그대로 남으며, 비활성화되고 사유로 `호스트가 UP 상태가 아님`이 표시됩니다.

> 💡 **참고:** 위 표는 자주 나타나는 사유만 정리한 것입니다. 그 밖의 사유는 화면에 그대로 표시됩니다. 사유가 `라이브`만 막는 것이면 `콜드`로는 옮길 수 있습니다.

## 하드웨어 변경 뒤 조치

노드의 메모리를 늘리거나 줄이고, CPU를 바꾸거나 BIOS에서 하이퍼스레딩(SMT)을 켜고 끈 뒤에 할 일입니다. 노드를 끄기 전에는 [인스턴스 마이그레이션](#인스턴스-마이그레이션)으로 인스턴스를 다른 노드로 옮겨 둡니다.

### 메모리를 바꾼 뒤

**메모리를 늘린 경우** 노드가 다시 켜지면 인스턴스를 배치할 수 있는 양인 **할당 가능 메모리**가 자동으로 늘어납니다. 따로 할 일은 없고, 바뀐 값은 `할당 가능 메모리 변경` 이벤트로 확인합니다.

**메모리를 줄였거나 자동으로 늘어나지 않은 경우**에는 할당 가능 메모리가 이전 메모리 기준으로 남습니다. 할당 가능 메모리를 줄이면 실행 중인 인스턴스가 멈출 수 있어 자동으로 바꾸지 않기 때문입니다. 이때 컴퓨트 노드 상세의 **리소스** 탭 메모리 영역에 아래 안내가 표시되고, 목록의 **메모리 오버커밋 최대 비율** 칸에 `(재계산 필요)`가 붙습니다. 같은 내용이 이벤트로도 남습니다.

> 물리 메모리 변경(64 GB → 32 GB). 설치 노드에서 recompute_guest_cap 플레이북을 실행하세요.

안내가 보이면 CloudiA를 설치한 노드에서 설치에 쓴 인벤토리로 아래 명령을 실행합니다. `<노드 이름>`에는 안내가 뜬 노드의 이름을 넣고, 여러 노드는 쉼표로 이어 씁니다.

```bash
cd <설치 디렉터리>/cloudia-erecto
ansible-playbook -i <인벤토리 파일> playbooks/maintenance/recompute_guest_cap.yml -e guest_cap_nodes=<노드 이름>
```

실행이 끝나면 노드별로 다음 값이 출력됩니다.

| 출력 | 뜻 |
| --- | --- |
| `MemTotal` | 지금 노드의 물리 메모리 |
| `cap before` · `cap now` | 실행 전과 후의 할당 가능 메모리(바이트) |
| `computed` | 새로 계산한 할당 가능 메모리 |
| `result APPLY` | 새 값을 적용했습니다 |
| `result SKIP:usage` | 실행 중인 인스턴스가 많아 적용하지 않았습니다(아래 주의 참고) |
| `result FAILED: …` | 적용하지 못했거나, 적용한 값을 노드에서 확인하지 못했습니다 |

적용되면 화면의 안내가 사라지고, 바뀐 메모리 기준으로 인스턴스를 배치합니다. 안내가 사라지는 데 1분 정도 걸릴 수 있습니다.

`result`가 `APPLY`가 아닌 노드가 하나라도 있으면 플레이북은 마지막에 실패로 끝나고, 그 노드의 안내는 그대로 남습니다. 출력된 이유를 확인해 조치한 뒤 그 노드만 다시 실행합니다.

> ⚠️ **주의:** 메모리를 줄인 경우, 노드에서 실행 중인 인스턴스가 새 할당 가능 메모리의 90% 이상을 쓰고 있으면 적용하지 않고 실패로 끝납니다(`result SKIP:usage`). 실행 중인 인스턴스를 보호하려는 것입니다. 인스턴스를 다른 노드로 옮긴 뒤 같은 명령을 다시 실행합니다.

### CPU를 바꾼 뒤

CPU를 교체하거나 하이퍼스레딩 설정을 바꾸고 재부팅하면, 노드의 vCPU 총량(**논리 CPU 수**의 전체 값)이 자동으로 다시 계산됩니다. 따로 실행할 명령은 없고, 바뀐 값은 이벤트에서 확인할 수 있습니다. 재부팅하지 않고 운영체제에서 하이퍼스레딩만 바꾼 경우에는 다음 재부팅 때 반영됩니다.

> ⚠️ **주의:** CPU 수가 줄어 이미 할당된 vCPU가 새 총량을 넘으면, 그 노드는 할당이 총량 아래로 내려갈 때까지 인스턴스를 더 받지 않습니다. 이 노드에서 멈춘 인스턴스를 다시 시작하거나 이 노드로 옮기는 작업도 거절될 수 있습니다. 실행 중인 인스턴스는 그대로 동작합니다. 필요하면 인스턴스를 다른 노드로 옮깁니다.
