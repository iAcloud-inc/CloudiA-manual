# 노드 접속 계정과 SSH 포트

Cloud:iA 노드끼리 SSH 로 접속할 때는 root 가 아니라 전용 서비스 계정 `cloudia-svc` 를 씁니다. 그래서 고객사 보안 기준에 따라 노드의 root SSH 로그인을 막거나(`PermitRootLogin no`) SSH 포트를 22 가 아닌 값으로 쓸 수 있습니다. 이 문서는 그 전에 고객사가 준비할 사항과 적용 순서를 설명합니다.

> 💡 **참고:** 이 문서는 노드 간 SSH 에 서비스 계정을 쓰는 Cloud:iA v1.6.3 이상에 적용됩니다.

## 개요

### 무엇이 서비스 계정으로 접속하는가
아래 작업이 다른 노드에 SSH 로 접속할 때 `cloudia-svc` 계정을 씁니다. 각 노드의 root 가 자기 SSH 키로 다른 노드의 `cloudia-svc` 에 접속합니다.

- Ceph 관리 (Cloud:iA 가 구축한 Ceph 인 경우)
- 노드 간 파일 복사 (이미지 복사, 가상머신 이전 등)
- 노드 추가·업데이트 도구 (관리자 계정으로 도구를 실행하는 구성에서는 고객사 관리자 계정으로 접속합니다. 아래 **sudo 권한** 참고)

Cloud:iA 서비스(호스트 에이전트, 데이터베이스, keepalived 등)는 지금처럼 root 로 동작합니다. 바뀌는 것은 노드끼리 SSH 로 접속하는 계정입니다. 이중화 데이터베이스가 상대 노드 상태를 확인할 때는 SSH 를 쓰지 않습니다.

서비스 계정 이름은 설치 때 다른 이름으로 정할 수 있습니다. 이 문서의 `cloudia-svc` 는 기본 이름입니다.

### 운영자 접속
운영자는 각자의 계정으로 노드에 접속한 뒤 `sudo -i` 로 root 권한을 얻어 작업합니다. 이 매뉴얼에서 "root 권한으로 실행"한다고 적은 절차는 이렇게 접속해 실행합니다.

## 고객사 사전 준비

### 노드 간 SSH
- 클러스터 노드끼리 직접 SSH 접속을 허용해야 합니다. 서버 간 직접 SSH 를 금지하는 환경에서는 노드 간 파일 복사가 동작하지 않습니다.
- `cloudia-svc` 의 SSH 키 인증 접속을 허용해야 합니다. SSH 서버 설정에서 `AllowUsers`·`AllowGroups` 로 접속 계정을 제한한다면 `cloudia-svc` 를 포함합니다.

### sudo 권한
구성에 따라 둘 중 하나를 고릅니다. 설치 전에 정해야 합니다. 어느 쪽이든 sudo 설정에 `Defaults requiretty` 를 두지 않습니다.

| 구성 | 필요한 sudo 권한 |
|---|---|
| Cloud:iA 가 구축한 Ceph 를 쓰는 구성 | `cloudia-svc` 에 비밀번호 없는 sudo(`NOPASSWD: ALL`)가 **반드시** 필요합니다. Ceph 관리 도구(cephadm)가 각 노드에서 비밀번호 없이 sudo 를 실행하기 때문입니다. 설치가 `/etc/sudoers.d/cloudia-svc` 를 만듭니다 |
| Ceph 를 쓰지 않거나 외부 Ceph 에 연결만 하는 구성 | 비밀번호 없는 sudo 를 허용할 수 있으면 위와 같습니다. 허용하지 않으면 `cloudia-svc` 에는 sudo 권한을 주지 않고, 노드 추가·업데이트 도구를 고객사 관리자 계정과 그 계정의 sudo 비밀번호로 실행합니다. 이때 관리자 계정에 비밀번호 sudo 권한(`(ALL) ALL`)이 필요합니다(이 문서에서 "관리자 계정으로 도구를 실행하는 구성") |

### 비밀번호 만료
- `cloudia-svc` 는 비밀번호 만료 정책에서 제외합니다(`chage -M -1 cloudia-svc`).
- 관리자 계정으로 도구를 실행하는 구성에서는 관리자 계정 비밀번호가 만료돼도 되지만, 노드 추가·업데이트 때 현재 비밀번호가 필요합니다.

### SSH 포트
노드 SSH 포트는 기본 22 이며, 설치 때 다른 포트를 지정할 수 있습니다. 22 가 아닌 포트를 쓰려면 설치 전에 다음을 준비합니다. 설치는 노드의 SSH 서버 설정을 바꾸지 않습니다.

- 모든 노드의 SSH 서버가 그 포트로 접속을 받도록 열어 둡니다.
- SELinux 가 `Enforcing` 이면 그 포트에 SSH 포트 라벨을 붙입니다. 예: `semanage port -a -t ssh_port_t -p tcp <포트>`
- 고객사 외부 방화벽·스위치 ACL 에서 노드 사이, 운영자 접속 구간에 그 포트를 허용합니다.

Cloud:iA 방화벽은 설치 때 이 포트를 허용하는 규칙(설명 `ssh`)을 만듭니다. 설치 후 포트를 바꿀 때 방화벽 규칙을 바꾸는 순서는 [방화벽](../../network/firewall/firewall.md)의 **SSH 포트를 바꿀 때**를 참고합니다.

### 노드를 추가할 때
root SSH 로그인을 막은 뒤에는 새 노드에 root 로 접속할 수 없으므로, 노드를 추가하기 전에 새 노드에 다음을 준비합니다. 컨트롤 노드는 설치를 실행한 노드이고, 그 root 공개키는 `/root/.ssh/id_ed25519.pub` 입니다.

- 비밀번호 없는 sudo 를 쓰는 구성: `cloudia-svc` 계정을 만들고, 비밀번호 없는 sudo 를 설정하고, 컨트롤 노드 root 공개키를 `cloudia-svc` 의 `~/.ssh/authorized_keys` 에 등록합니다.
- 관리자 계정으로 도구를 실행하는 구성: 관리자 계정(비밀번호 sudo 가능)의 `~/.ssh/authorized_keys` 에 컨트롤 노드 root 공개키를 등록합니다. `cloudia-svc` 는 노드 추가 과정에서 만들어집니다.

## root SSH 로그인 차단 적용 순서

> ⚠️ **주의:** 서비스 계정으로 전환하는 업데이트를 마치기 전에 `PermitRootLogin no` 를 적용하면 Ceph 관리, 노드 간 파일 복사, 데이터베이스 이중화 판정이 실패합니다. 반드시 아래 순서를 지킵니다.

1. Cloud:iA 를 v1.6.3 이상으로 업데이트합니다. 이 업데이트가 노드 간 SSH 를 서비스 계정으로 전환합니다. 업데이트하는 동안에는 root SSH 로그인이 허용돼 있어야 합니다. v1.6.3 이상으로 새로 설치한 클러스터는 이미 서비스 계정을 쓰므로 2단계부터 진행합니다.
2. 관리자 계정으로 도구를 실행하는 구성이라면, 기존 모든 노드의 관리자 계정 `~/.ssh/authorized_keys` 에 컨트롤 노드 root 공개키를 등록합니다.
3. 설치 담당자가 적용 전 점검을 실행해 모든 항목이 통과하는지 확인합니다. 점검은 root SSH 없이 서비스 계정 경로만으로 노드 간 접속, Ceph 관리, 데이터베이스 상대 확인, 노드 간 파일 복사가 되는지 봅니다.
4. 점검이 통과한 뒤 노드의 SSH 서버 설정에 `PermitRootLogin no` 를 적용합니다.

적용 후 문제가 생기면 먼저 SSH 서버 설정을 되돌려 root 키 인증 접속을 다시 허용한 뒤 원인을 확인합니다.

> 💡 **참고:** 처음부터 root SSH 로그인이 막힌 노드에 Cloud:iA 를 새로 설치하는 것은 지원하지 않습니다. 설치하는 동안에는 root SSH 로그인을 허용해야 합니다.

## 운영 참고

### 서비스 계정을 복구한 뒤에도 Ceph 관리가 실패할 때
Cloud:iA 가 구축한 Ceph 를 쓰는 구성에서, `cloudia-svc` 의 셸이나 SSH 키가 잠시 깨졌다가 복구된 뒤에도 Ceph 관리가 그 노드에 계속 실패할 수 있습니다(`ceph cephadm check-host <호스트>` 실패). Ceph 관리 도구가 노드와 맺어 둔 SSH 연결을 다시 쓰기 때문에, 계정만 복구해서는 바로 풀리지 않습니다.

이때는 root 권한으로 아래 명령을 실행해 Ceph 관리 도구의 SSH 연결을 초기화한 뒤 다시 확인합니다.

```
ceph mgr fail
ceph cephadm check-host <호스트>
```
